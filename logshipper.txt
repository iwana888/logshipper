# 日志抓取程序需求规格说明

## 一、背景与目标

现有两套应用实例，日志以文件形式落在本机磁盘。需要将两个实例的日志集中推送到单实例 Loki，供 Grafana 统一查询排查。官方 Promtail 功能冗余（pipeline stages、服务发现、多租户、metrics 等均用不上），且二进制体积大、配置复杂。因此自研一个轻量抓取程序，只做“读文件 → 推 Loki”这一件事。

**目标**：单实例、单进程、零外部依赖（除 Loki 外），部署在每台应用服务器上，跟随应用实例一一对应。日志不丢，允许少量重复（至少一次语义）。

---

## 二、运行形态

- **部署位置**：每台应用服务器本地运行一个抓取进程，只读本机日志文件，不跨机读共享存储。
- **进程模型**：单进程、单线程主循环即可（日志量不大，不需要多线程并发读多个文件；如需多文件，可扩展为“每文件一线程”，首版不做）。
- **启动方式**：作为系统服务（systemd / Windows Service）随机器启动，或由应用启动脚本拉起。
- **配置来源**：独立配置文件（INI 或 JSON），启动时读取，不支持热加载（改配置需重启）。

---

## 三、功能需求

### FR-1 日志文件读取

- 按配置的**文件路径列表**（支持通配符，如 `/var/log/myapp/*.log`）发现日志文件。
- 按行读取，保留原始行内容（含时间戳前缀），不做格式解析之外的任何改写。
- 单行长度上限 **256KB**（Loki 默认上限），超长行截断并在末尾追加 `...[truncated]` 标记，同时记录一条本地告警日志。
- 文件不存在时**不崩溃**，按轮询间隔重试打开。

### FR-2 读取位置（offset）持久化

- 每个文件按 **`路径 + inode + offset`** 三元组记录读取位置。
- 持久化到本地文件（如 `positions.json`），**每成功推送一批后落盘一次**，不做每行落盘。
- 程序重启后，按持久化记录恢复读取位置；若文件 inode 变化或文件大小小于记录的 offset，视为轮转/截断，**offset 归零重读**。
- 持久化写入采用“写临时文件 + rename”方式，防止写一半断电导致 positions 文件损坏。

### FR-3 文件轮转与截断检测

- 每次轮询前 `stat` 当前路径，比对 inode：
  - inode 变化 → 旧 fd 读完剩余内容后关闭，打开新文件，offset 归零。
  - inode 不变但 `st_size < last_offset` → 判定为 truncate，offset 归零。
- 支持 `logrotate` 的 `rename + 新建` 和 `copytruncate` 两种模式。

### FR-4 批处理

- 攒批条件（先到先触发）：
  - **行数达到 100 行**，或
  - **距上次推送超过 2 秒**，或
  - **累计字节数达到 256KB**。
- 一批内的日志按原始顺序保留，不重排。

### FR-5 时间戳处理

- 尝试从日志行**开头**解析时间戳，支持配置的时间格式（首版支持 `YYYY-MM-DD HH:MM:SS` 和 Unix 秒/毫秒两种）。
- 解析成功 → 使用日志自带时间戳（转为纳秒）。
- 解析失败 → 使用**读取时刻**（`GetTick64` 转 Unix 纳秒），并在该行前不做任何标记（保持原始内容）。
- **同一批内时间戳必须单调不减**（Loki 要求同一 stream 内时间戳有序）；若解析出的时间戳乱序，按“上一行时间戳 + 1 纳秒”修正，并记录一条本地告警。

### FR-6 标签设计

每条推送携带以下标签（**低基数**，禁止把时间戳、行号、trace_id 等高基数字段放进标签）：

| 标签 | 来源 | 示例 |
|---|---|---|
| `job` | 配置项，固定值 | `myapp` |
| `instance` | 配置项，**每台机器不同** | `app-1` / `app-2` |
| `level` | 从日志行解析（可选） | `info` / `error` |

`level` 解析规则可配置（如正则 `\[(INFO|WARN|ERROR)\]`），解析不到则不打该标签（或统一标 `unknown`，二选一，配置决定）。

### FR-7 推送 Loki

- 协议：`POST /loki/api/v1/push`，`Content-Type: application/json`。
- 请求体格式：

```json
{
  "streams": [
    {
      "stream": {"job": "myapp", "instance": "app-1", "level": "error"},
      "values": [
        ["1730610600000000000", "原始日志行"],
        ["1730610601000000000", "原始日志行"]
      ]
    }
  ]
}
```

- 同一批内按 `stream` 标签组合**分组**，不同标签组合拆成多个 stream 对象。
- 支持 **gzip 压缩**（`Content-Encoding: gzip`），配置项开关，默认开启。
- 请求超时 **5 秒**。
- 认证：支持可选的 `Authorization: Bearer <token>` 头（Loki 开启多租户或反向代理鉴权时需要）。

### FR-8 失败重试

- 推送失败（网络错误、5xx、429）→ **指数退避重试**：1s → 2s → 4s → 8s → 16s → 30s 封顶，无限重试直到成功或进程退出。
- **重试期间 offset 不前进**，同一批数据在内存中保留，下次重试时重发。
- 4xx（除 429 外，如 400 格式错误）→ **不重试**，丢弃该批，记录本地错误日志（含响应体），offset 前进（避免卡死）。这种情况说明是程序 bug 或配置错误，重试无意义。
- 内存中最多缓冲 **10000 行**；达到上限时**阻塞读取**（背压），不丢弃。

### FR-9 优雅退出

- 收到 `SIGTERM` / `SIGINT`（或 Windows Service Stop）后：
  - 停止读取新数据；
  - 将内存中未推送的批次**尝试推送一次**（超时 5 秒）；
  - 落盘 positions；
  - 退出。
- 退出超时 **10 秒**，超时强制退出，未推送数据丢弃（但 positions 不前进，下次启动会重读）。

## 四、非功能需求

### NFR-1 性能

- 单实例日志量假设 **< 10GB/天**，程序 CPU 占用 < 5%，内存占用 < 100MB。
- 从日志写入文件到推送到 Loki，延迟 < 5 秒（正常网络下）。

### NFR-2 可靠性

- Loki 不可用期间，日志在本地文件堆积（应用照常写），程序 offset 不前进，恢复后自动补推。
- 程序崩溃重启后，不丢日志（最多重复最后一批）。

### NFR-3 可观测性

- 程序自身日志输出到 **stderr**（由 systemd 收集）或独立文件，包含：
  - 启动/退出；
  - 每次推送成功的行数、字节数、耗时；
  - 推送失败的原因和重试次数；
  - 文件轮转/截断事件；
  - 超长行截断、时间戳解析失败等异常。
- **不内置 metrics 端点**（首版不做，排查靠程序日志 + Loki 自身指标）。

### NFR-4 依赖

- 仅依赖 FPC RTL 和 Lazarus 自带单元：`fphttpclient`（HTTP）、`zlib`（gzip）、`BaseUnix`/`Windows`（stat/信号）、`fpjson` 或手拼 JSON。
- 不引入 mORMot 等重型框架（保持二进制小、部署简单）。

## 五、配置项（示例 INI）

```ini
[loki]
url=http://loki.internal:3100/loki/api/v1/push
token=
gzip=true
timeout_ms=5000

[agent]
job=myapp
instance=app-1
poll_interval_ms=200
batch_max_lines=100
batch_max_bytes=262144
batch_max_delay_ms=2000
buffer_max_lines=10000
; Optional: write this program's own status log to a file, in addition to the
; console (the console always stays full). Keep it OUTSIDE the tailed globs.
; By default the file gets ONLY error lines; use log_file_level=info to also
; keep INFO/WARN (incl. the 'pushed N lines' heartbeat) for liveness checks.
; log_file=/var/log/tc/logshipper.log
; log_file_level=error
; log_file_max_bytes=10485760
; log_file_max_files=5

[files]
; Match ONLY the live, UNCOMPRESSED log (e.g. *.log). Do NOT match rotated
; compressed files like *.gz — this tool does NOT decompress logs.
paths=/var/log/myapp/*.log
positions_file=/var/lib/logshipper/positions.json
max_line_bytes=262144

[timestamp]
formats=%Y-%m-%d %H:%M:%S;unix_ms
level_regex=\[(INFO|WARN|ERROR|DEBUG)\]
```

## 六、不做的范围（明确排除）

- ❌ Pipeline stages（正则提取、字段替换、drop 规则）——日志格式由应用控制，不做二次加工。
- ❌ 服务发现（K8s、Consul、文件通配之外的动态发现）——路径静态配置。
- ❌ 多租户——单租户自用。
- ❌ Metrics 端点——首版不做。
- ❌ 热加载配置——改配置重启。
- ❌ 多文件并发读取——首版单线程顺序读，文件多时按轮询依次处理。
- ❌ 日志内容解析成结构化字段——只打 `level` 一个标签，其余原样保留。

## 七、验收标准

| # | 场景 | 预期 |
|---|---|---|
| 1 | 正常写入日志 | 5 秒内可在 Grafana 查到 |
| 2 | 程序 kill -9 后重启 | 从上次 offset 继续，不丢不重（最多重复最后一批） |
| 3 | Loki 停止 5 分钟后恢复 | 恢复后自动补推这 5 分钟的日志 |
| 4 | logrotate rename 轮转 | 旧文件读完，新文件从 0 开始，不丢不重 |
| 5 | logrotate copytruncate 截断 | 检测到 size 变小，offset 归零，不丢 |
| 6 | 超长行（>256KB） | 截断并标记，不崩溃，不阻塞后续行 |
| 7 | 日志行无时间戳 | 使用读取时刻，正常推送 |
| 8 | 两个实例同时运行 | Grafana 按 `instance` 标签能区分，不混淆 |
| 9 | 推送返回 400 | 丢弃该批，记录错误，offset 前进，不卡死 |
| 10 | 推送返回 429/503 | 指数退避重试，offset 不前进，不丢日志 |
| 11 | SIGTERM 退出 | 10 秒内退出，positions 已落盘 |
| 12 | 磁盘满 / positions 文件不可写 | 记录错误，进程不崩溃，继续尝试 |
